### 5. Residual stutter from CFS throttling  *(perf — lowest priority; warm nav already smooth)*
- [x] **In-extension: software-render CPUs now configurable, default 8** (`manifests.ts` + `OpenShiftDeployConfig.cpu` + a **Software-render CPUs** field on the OpenShift tab). Container sees `nproc=16` but was capped at 6; Gazebo/Ogre size thread pools to nproc → bursts exceed quota → ~98% of 100ms periods throttled → micro-freezes even at avg RTF ~1.0. 8 cores (default) widen the quota so bursts fit and leave headroom for multi-robot; users can dial it to their node sizes (validated: 1–64, `assertCpuCount`). **Not yet live-validated on the cluster.**
- [x] **Image-level (the proper fix): cap render/physics thread pools to the quota** — `entrypoint-gazebo.sh` now derives the cgroup CPU quota (v2 `cpu.max`, v1 fallback) and caps `OMP_/OPENBLAS_/LP_/MESA_/GALLIUM_NUM_THREADS` to it, so pools stop oversubscribing at *any* core count. Only caps when a quota exists (the unlimited local path is left alone); override with `PHYSICAL_AI_CPU_CAP`. Complementary to the CPU bump. See `docs/stories/story5-image-thread-caps.md`. **Needs an image rebuild + push by the user, then live-validate.**
  - Not env-cappable: Ogre2 render workers and DART physics *island* threads (a world `<physics>` SDF setting). Revisit the world file only if stutter persists after the env caps.
- [x] **Alternative (real smoothness fix): GPU** — offloads the render off the CPU entirely (the `useGpu` path already requests `nvidia.com/gpu` + hardware rendering). Confirmed on `sgahlot-pd-extn`: 6× A10G GPU nodes with the NVIDIA GPU operator running, one GPU free (`ip-10-0-245-11`, ~7 CPU free). **Gap found + fixed:** the GPU nodes are tainted `g5-gpu=true:NoSchedule` but the `useGpu` manifest emitted no toleration, so a GPU pod would sit Pending. Added a configurable **GPU node taint toleration** (`OpenShiftDeployConfig.gpuToleration` as `key[=value][:effect]`, default `g5-gpu=true:NoSchedule`; a bare `key:effect` → `Exists`), parsed by `parseGpuToleration` and emitted as a pod `tolerations` entry only on the GPU path. New optional field on the OpenShift tab (shown when GPU is ticked). Tests added (manifest builder + parser + UI).
  - **First GPU-on-OCP live test (`ip-10-0-245-11`) — two bugs found + fixed:**
    1. **noVNC "Connect" never rendered → Xvfb segfault (image-level).** Xvfb's `+extension GLX` init bound `libnvidia-egl-gbm`/`libEGL_nvidia` and SIGSEGV'd — there is **no `/dev/dri` render node** in an NVIDIA-operator pod (it exposes `/dev/nvidia*` only). Xvfb's death cascaded: openbox/x11vnc couldn't open the display, the GUI aborted (SIGABRT), websockify looped `Connection refused` on 5900 → the browser showed the noVNC **Connect** screen that bounced. **Root cause (deeper than first thought):** the crash is in **glvnd's EGL *vendor* selection**, which `LIBGL_ALWAYS_SOFTWARE`/`GALLIUM_DRIVER` do **not** control (those steer only Mesa's GL/GLX). glvnd picks the EGL vendor by the lowest priority number in `egl_vendor.d` (here `10_nvidia.json` < `50_mesa.json`), so Xvfb got NVIDIA EGL regardless. A first fix that only set `LIBGL_ALWAYS_SOFTWARE=1 GALLIUM_DRIVER=llvmpipe` for Xvfb/GUI **still segfaulted** (confirmed live). **Fix (`entrypoint-gazebo.sh`):** pin the EGL *vendor* explicitly per process via `__EGL_VENDOR_LIBRARY_FILENAMES`, resolving each vendor's ICD **by name** (`_pai_find_egl_vendor nvidia|mesa`) so it's independent of the cluster's glvnd priority numbering (Mesa could be `10_` on another cluster). Xvfb + GUI → Mesa vendor + `__GLX_VENDOR_LIBRARY_NAME=mesa` + software GL (via `XVFB_GUI_GL`, guarded `[@]+` expansion); the **gz server** → NVIDIA vendor (via `GZ_SERVER_GL`) so its headless EGL binds the GPU. **Validated live in the pod:** Xvfb survives on the Mesa vendor (llvmpipe GLX, x11vnc opens the display); the server shows up in `nvidia-smi` (type `G`, ~106 MiB) rendering sensors on the A10G. So on a no-DRI cluster only *sensor* rendering is GPU-accelerated; the **GUI canvas stays CPU-rendered** (hardware GLX for the GUI would need `/dev/dri`, which the operator doesn't expose).
    2. **GPU pod CPU too low for the software GUI (manifest-level).** Because the GUI stays software on no-DRI, the old GPU-path `requests:1/limits:2` throttled it. Bumped to a fixed **`GPU_POD_CPU` guaranteed** (requests==limits); the user CPU field remains software-render only (GPU-pod CPU is bounded by node size, not preference). Tests updated.
  - **Second GPU-on-OCP live test — navigation slow-to-start (~20s) + jumpy motion (still CFS throttling).** Diagnosed live in the pod: at `GPU_POD_CPU=6` the pod throttled **~97% of scheduling periods even at idle** (10s delta: `throttled +97 / periods +100`; `cpu.max = 600000 100000`). Cause: the software GUI (`gz sim -g`, llvmpipe) alone draws **~3 cores at idle**, + server ~0.6 + pre-warmed Nav2 ~1.5 → ~5 cores idle, bursting past the 6-core quota during nav. The GPU doesn't help the GUI — no `/dev/dri`, so only the *server's sensor* render is GPU-accelerated. Two fixes:
    - **CPU: `GPU_POD_CPU` 6→7 (extension).** 7 is the most an 8-vCPU g5.2xlarge fits (7000m pod + ~474m node-system ≈ 7474m < ~7500m allocatable — the node's last free core). Gives idle demand headroom so the throttle eases. Tests updated.
    - **GUI cost: disabled world shadows (image, `tb3_sandbox.sdf.xacro` `<cast_shadows>false</cast_shadows>` on the sun).** Ogre2 software shadow-map passes should be among the priciest part of the llvmpipe GUI render. **Live result: shadows were NOT the dominant cost** — with the fresh image the GUI still drew ~3.5 cores (`gz sim -g` at 350–372% in `top`). Kept off anyway (cheap, harmless), but it didn't move the needle.
  - **Third finding — the residual jumpiness is CPU *saturation*, and it's FIXED by clamping the GUI's llvmpipe threads (image-level).** After the 7-CPU bump throttling was largely gone (idle delta ~51% of periods, `throttled_usec` ~0.16 s/10 s vs ~6 s before), yet navigation was still jumpy with the transient "double robot". Root cause pinned live via `top -H`: the software GUI's cost is **llvmpipe *rasterizer* threads** (7 `llvmpipe-0..6` threads each ~40%, the Qt `QSGRenderThread` only ~8%), and the GUI **free-runs** (renders as fast as it can), so it consumes **~1 core per llvmpipe thread**. The Story-5 thread cap sizes that pool to the whole quota (7) — exactly backwards for the GUI: it burned ~3.5 cores and starved the gz *server's* physics thread, so RTF swung **0.39 → 1.46** step-to-step (= jerky motion; the "2-robot flash" is the GUI drawing a stale pose during a stall — still only `robot_1` in `gz model --list`). **Key correction to the earlier framing:** this is NOT a hard node-size ceiling and the GPU is working as intended (server sensors on the A10G; the GUI is software only because there's no `/dev/dri`). **Fix (`entrypoint-gazebo.sh`): clamp the GUI's llvmpipe pool to 2 threads** (`PHYSICAL_AI_GUI_LP_THREADS=2`, layered as a GUI-only `env` prefix over the global cap) **+ renice the GUI to 19** (`PHYSICAL_AI_GUI_NICE`, belt-and-suspenders; we can't raise the server's priority — negative nice needs `CAP_SYS_NICE`, denied in-cluster). **Proven live in the pod:**
    - Pinning the running GUI to 2 cores (`taskset`): GUI 350% → 180%, **RTF snapped to a rock-steady ~1.000** (was 0.39–1.46).
    - Relaunching the GUI with `LP_NUM_THREADS=2` (the portable, baked-in mechanism — no affinity): GUI 350% → **170%**, server rose to 90% (no longer starved), **RTF ~1.000** across all samples.
    - x11vnc downsamples the GUI for noVNC regardless, so the lower GUI frame rate is invisible to the user.
    - **Further lever if ever needed:** lower GUI resolution (cuts absolute fill). Not needed at threads=2. A bigger GPU node or a `/dev/dri` render node (GUI on GPU) would remove the software-GUI cost entirely, but is not required for smooth nav now.
    - The **"2 robots for 2–3s" report was benign** — only `robot_1` existed (`gz model --list`, single spawn in the process tree); the GUI briefly drew the model at the world origin before its spawn pose/TF settled, then snapped to the real pose.
  - ✅ **VALIDATED LIVE (fresh rebuild + redeploy, `ip-10-0-245-11`).** With the GUI llvmpipe clamp + renice baked into the image and `GPU_POD_CPU=7`: the pod came up with `Launching Gazebo GUI (llvmpipe threads=2, nice=19)`, GUI at 180% (was 350%), RTF steady ~1.000, and a full spawn→navigate ran **smooth end-to-end** ("buttery motion all the way to destination"). The RTF/CPU smoothness fix is confirmed working; the "jumping in place at start" turned out to be a **separate Nav2 issue**, now root-caused and fixed (see item 5a below).
  - **Latent gap noted while investigating (backlog, not fixed — nothing broken):** the pre-warm seeds `/initialpose` with a **hardcoded `orientation {w: 1.0}` (yaw 0), ignoring the real spawn yaw**, and a loose covariance (`entrypoint-nav2.sh:88-90`). Harmless for the default yaw-0 spawn, but a non-zero-yaw spawn would start AMCL mis-headed → longer, jumpier convergence. If it ever resurfaces: seed the actual `SPAWN_YAW` (as a quaternion) and a tighter covariance (we know exactly where the robot was placed, so AMCL can trust it).
  - **Possible follow-up (extension, offered):** now that the GUI only needs ~2 cores, `GPU_POD_CPU=7` is likely more than necessary — a smaller request (e.g. 5) would schedule on more/ smaller GPU nodes. Validate live before changing.

### 5a. Startup "jumping in place" (~15–30 s) → cold-start **global-planner** costmap artifact  *(nav quality)*
- [x] **Re-root-caused live with second-by-second instrumentation (GPU pod `9hkwk`, project `sgahlot-pd-extn`).** The first fix attempt (commit `bb6adaf` — clear costmaps at *pre-warm* time) **did not work live**, so the cold start was instrumented directly (restart Nav2 by PID, fire a goal the instant nav goes active, record `cmd_vel`/planner/costmap). The stall is the **global planner** failing, not the MPPI controller and not localization (AMCL well-localized at (−1.98, −0.52) immediately). During the stall the Nav2 log shows, on repeat:
  ```
  [WARN] planner_server: GridBased plugin failed to plan from (-1.35,1.32) to (1.50,1.50):
                          "Failed to create plan with tolerance of: 0.500000"
  [INFO] global_costmap: Received request to clear entirely the global_costmap   ← recovery
  [INFO] behavior_server: Running spin → Running wait → Running backup           ← BT recovery
  ... (repeats, ~8 planner failures) ... Goal finished with status: SUCCEEDED
  ```
  The robot drives the open initial stretch fine (smooth ramp to 0.45 m/s), then a global **replan fails** because the cold global costmap transiently holds bad cells blocking every route to the goal (early laser scans mis-projected while the sim clock/TF lag during the CPU-heavy launch). Nav2's recovery clears the **global** costmap and retries until a clean refill opens a path — that's the ~15 s "jumping in place." The earlier "Failed to make progress" (MPPI `SimpleProgressChecker`) seen on other runs is a downstream symptom of the same no-valid-path condition; the driver is the planner. `collision_monitor`'s `[FootprintApproach]: Polygon shape is not set yet` spam is benign startup noise, not the blocker.
- [x] **Confirmed it's a settling effect (not tuning), and intermittent.** Repeated goals on one bringup showed planner failures **diminish to zero**: 8 → 8 → 1 → 0 → 0 → 0. It self-heals through *driving* (recovery clears + re-observation), not pure waiting. A goal ~500 s after bringup ran clean in 18 s; near-cold goals took ~30 s. One cold run had 8 failures, another had 0 — a startup **race**, so the fix must be robust, and Nav2's own recovery remains the backstop.
- [x] **Fix (extension-level, no image rebuild): clear both costmaps once per cold bringup, at *goal-dispatch* time (not pre-warm).** Two corrections over `bb6adaf`: (1) the clear is moved from pre-warm to **just before the first `send_goal`** — by then the clock has usually settled, so the refill stays clean (pre-warm was too early, phantoms re-accumulated); (2) it now matters for the **global** costmap/planner, not just local (it clears both). When `#ensureNav2Running` launches a fresh bringup it marks `nav2ClearPending` (keyed by `#navTargetKey`); the first goal consumes the mark, runs `#clearNav2Costmaps` (both maps), settles ~2 s (`NAV2_COSTMAP_REFILL_MS`), then plans. A **genuinely warm sim we never brought up is never marked** → no added latency; the mark is consumed once per bringup → subsequent goals skip it. Best-effort (a clear hiccup never blocks Navigate); covers podman + OpenShift (shared path). Backend tests updated (cold clears both maps before the goal; warm path doesn't; second goal doesn't re-clear) — **150 backend tests green**. **✅ VALIDATED LIVE (fresh extension rebuild + redeploy):** spawn→navigate ran **smooth with no jumping in place** — the cold-start global-planner stall is resolved. Option 2 (gate the first goal on sim-clock/RTF stability, not just TF) remains the escalation path if a very-early navigate ever stalls again, but was not needed.

### 6. Redeploy over an active deployment is a silent no-op  *(UX — backlog)*
- [ ] **Problem:** the sim image uses a **mutable tag** (`:noble-amd64`) and Deploy does an `oc apply`. If a deployment of the same name is already running and the emitted spec is unchanged, `apply` sees no diff → **no rollout**, so a freshly-pushed image is **never pulled** (the running pod keeps the old image; `imagePullPolicy: Always` only pulls on pod *creation*). Found live: after pushing a fixed image, the 21-min-old pod stayed on the old (crashing) image until the user deleted the deployment manually.
- [ ] **Options to consider:** (a) if a deployment with the target name already exists, **prompt the user** (redeploy/undeploy-first/cancel); (b) on redeploy, force a rollout so a new image is pulled even when the spec is unchanged (e.g. stamp a `kubectl.kubernetes.io/restartedAt`-style pod-template annotation, or delete+recreate). Note the CPU 1→6 change *did* change the spec, so once the extension is rebuilt a redeploy would roll out on its own — but that's incidental; the general mutable-tag case still needs a forced rollout.
