== Purpose

This document captures the architecture, component design, data flow, and key technical decisions for the Physical AI Podman Desktop extension. It is a living document — updated as the project evolves.

For work breakdown and progress tracking, see the link:podman-extension-plan.md[plan doc].

== Goals

[cols="1,3"]
|===
| Goal | Description

| Zero-CLI robotics dev
| Robotics engineers should be able to go from "install extension" to "running simulation" without touching a terminal

| Container-first robotics
| Provide curated ROS2 base images (currently Ubuntu 24.04) with a migration path toward Fedora/RHEL as official ROS2 packaging matures

| Local-to-cluster path
| Enable the transition from local Podman development to OpenShift deployment

| ROSCon demo-ready
| MVP must be demonstrable at ROSCon Toronto, September 2026
|===

== Component Design

=== Extension Backend (`packages/backend`)

The backend is the entry point loaded by Podman Desktop. It manages the extension lifecycle and provides the API surface for the frontend.

==== Responsibilities

* Extension activation/deactivation (`activate()` / `deactivate()`)
* Webview panel creation and media asset loading
* RPC bridge registration via `RpcExtension`
* Command registration (`physical-ai.open` — reopens the dashboard panel)
* Podman Engine interaction (image build/push/pull, container lifecycle, simulation management)
* Image build orchestration with `AbortController`-based cancellation
* Build/push progress tracking via in-memory `Map` instances
* Quay.io registry API queries

==== Key Files

[cols="1,2"]
|===
| File | Role

| `src/extension.ts` | Entry point — creates webview panel, wires RPC, registers `physical-ai.open` command
| `src/api-impl.ts` | `PhysicalAiApiImpl` — implements all API methods; private helpers use JS `#private` syntax (not RPC-callable)
| `src/progressLogs.ts` | `appendProgressLog()` — capped at 500 lines with truncation marker
| `package.json` | Extension manifest (contributes: commands, configuration with 17 settings grouped under 5 namespaces — general/simulation/catalog/build/openshift — each with a markdown-type section-title entry since Podman Desktop's config schema has no native sub-sections)
| `vite.config.js` | Builds to CJS, externalizes `@podman-desktop/api`
| `assets/ros2-jazzy-base/` | Bundled Containerfile + entrypoint for Jazzy base builds
| `assets/ros2-jazzy-sim/` | Jazzy simulation image: Containerfile, entrypoint-gazebo.sh, entrypoint-spawn-robot.sh, world SDF, noVNC landing page
| `assets/ros2-humble-base/` | Bundled Containerfile for Humble base builds
| `assets/ros2-humble-turtlebot3/` | Bundled Containerfile + entrypoint for Humble simulation builds
|===

=== Extension Frontend (`packages/frontend`)

The frontend is a Svelte 5 SPA rendered inside a Podman Desktop webview panel. It uses TailwindCSS for layout and `.pai-*` CSS classes (defined in `app.css`) for theming that adapts to Podman Desktop's light/dark mode.

==== Responsibilities

* Dashboard landing page; the Quick Links feature-card grid is shown only in Cards mode. Under the Sidebar/Tabs layouts it doubles as the `Home` destination and instead renders a guidance dashboard (welcome + get-started + live metrics + explore) so it doesn't duplicate the persistent nav (`physical-ai.general.navigationLayout` preference, S8-13)
* Image catalog browser with All/Curated views and pull progress _(APPENG-5770, done)_
* Image Builder for base and simulation images with Quick Start presets (Local host-native + OpenShift amd64) _(done)_
* Simulation page — launch, status, open in browser, stop & remove, add TurtleBot3, per-robot X/Y + **Navigate** (Jazzy: Nav2 `navigate_to_pose`; Humble: `cmd_vel`). Lidar/IMU sensors active on Mac (2026-08).
* In-extension Help page _(done)_
* ROS2 topic monitor — active topics, message types, pub/sub counts _(APPENG-5773, done)_
* Fleet status dashboard _(APPENG-5776, planned — Story 3)_

=== Shared Layer (`packages/shared`)

The shared package defines the API contract between frontend and backend, provides the RPC transport, and contains shared type definitions.

==== MessageProxy RPC Bridge

[source]
----
Frontend (RpcBrowser)                    Backend (RpcExtension)
        │                                        │
        │──── IMessageRequest ──────────────────►│
        │     { id, channel, args }              │
        │                                        │── calls registered method
        │◄─── IMessageResponse ──────────────────│
        │     { id, channel, body, status }      │
----

* Frontend calls `physicalAiClient.someMethod(args)` — the proxy serializes this as an `IMessageRequest` via `postMessage`
* Backend `RpcExtension` dispatches to the registered method on `PhysicalAiApiImpl`
* Response is sent back as `IMessageResponse` with status `success` or `error`
* 10-second timeout per request
* Podman Desktop webview does NOT deliver unsolicited backend-to-frontend messages — the frontend polls for progress updates instead of receiving push notifications

==== API Interface

The `PhysicalAiApi` abstract class defines the contract. Both the frontend proxy and backend implementation conform to it.

.Current API
[source,typescript]
----
export abstract class PhysicalAiApi {
  // Status
  abstract getStatus(): Promise<string>;

  // Image Catalog
  abstract listCatalogImages(namespace: string): Promise<QuayRepository[]>;
  abstract getImageTags(namespace: string, name: string): Promise<QuayTag[]>;
  abstract pullImage(fullImageName: string, tag: string): Promise<void>;
  abstract getPullProgress(image: string): Promise<PullProgress | null>;
  abstract listLocalImages(): Promise<string[]>;

  // Build & Push
  abstract buildBaseImage(tag: string, config: SimulationConfig): Promise<void>;
  abstract buildSimulationImage(tag: string, config: SimulationConfig): Promise<void>;
  abstract cancelBuild(tag: string): Promise<void>;
  abstract getBuildProgress(tag: string): Promise<BuildProgress | null>;
  abstract pushImage(tag: string): Promise<void>;
  abstract getPushProgress(tag: string): Promise<PushProgress | null>;
  abstract cancelPush(tag: string): Promise<void>;

  // Configuration
  abstract getDefaultNamespace(): Promise<string>;
  abstract getHostArch(): Promise<string>;
  abstract getCatalogViewMode(): Promise<'all' | 'curated'>;
  abstract setCatalogViewMode(mode: 'all' | 'curated'): Promise<void>;
  abstract getCatalogCuratedAllowlist(): Promise<string>;
  abstract getSimulationConfig(): Promise<SimulationConfig>;
  abstract saveSimulationConfig(config: SimulationConfig): Promise<void>;

  // Simulation lifecycle (Story 6)
  abstract launchSimulation(imageTag: string, containerName: string, options?: SimLaunchOptions): Promise<string>;
  abstract stopSimulation(containerId: string): Promise<void>;
  abstract deleteSimulation(containerId: string): Promise<void>;
  abstract listSimulationContainers(): Promise<SimContainerInfo[]>;
  abstract execInSimulation(containerId: string, command: string[]): Promise<ExecResult>;
  abstract openSimulationInBrowser(port: number): Promise<void>;

  // Topic Monitor (APPENG-5773)
  abstract listRosTopics(containerId: string): Promise<TopicInfo[]>;

  // Navigation (Navigate button, APPENG-5920 / APPENG-5981) — Jazzy Nav2; Humble cmd_vel fallback
  abstract sendNavigationGoal(containerId: string, robotName: string, x: number, y: number): Promise<NavigationGoalResult>;
}
----

== Data Flow

=== Image Catalog

[source]
----
User browses catalog ──► Frontend requests image list ──► Backend queries Quay API (public=true)
                                                                    │
                         Private repos are not listed without Quay auth
                                                                    │
User clicks "Pull"   ──► Frontend sends pull request  ──► Backend calls Podman pull
                                                                    │
                         Frontend polls getPullProgress ◄── Backend returns PullProgress
                         (every 500ms while active)         { status, layers, percent }

listLocalImages()    ──► Merges Podman Desktop engine image list with `podman images` CLI output.
                         Some Podman 5 / Podman Desktop builds return images with no tag names
                         (empty RepoTags); the CLI merge keeps those images visible under
                         "Locally Available" in the catalog.
----

=== Build & Push (Base Image and Simulation Image)

[source]
----
User clicks "Build"  ──► Frontend sends buildBaseImage/buildSimulationImage
                                │
                                ├── Backend resolves Containerfile asset directory
                                ├── (simulation) resolves SimulationProfile → assetDir
                                ├── (simulation) resolves SimulationBaseImage → ROS_BASE_IMAGE build-arg
                                ├── Backend calls containerEngine.buildImage() with AbortController
                                │
                         Frontend polls getBuildProgress ◄── Backend returns BuildProgress
                         (every 500ms while active)         { step, totalSteps, log, done, error, cancelled }

User clicks "Cancel" ──► Frontend calls cancelBuild(tag) ──► Backend aborts AbortController
                                                              Progress marked done immediately

User clicks "Push"   ──► Frontend sends pushImage(tag) with AbortController
                                │
                         Frontend polls getPushProgress  ◄── Backend returns PushProgress
                         (every 500ms while active)          { status, digest, logs, done, error, cancelled }

User clicks "Cancel push" ──► Frontend calls cancelPush(tag) ──► Backend aborts AbortController
                                                                  Progress marked done immediately

Registry presence ──► Frontend calls getImageTags for quay.io/ns/name:tag (public API)
                      Shows "exists in registry" / "not found" / "unavailable" (private/error)
----

=== Image Builder (wizard + build)

[source]
----
User configures Image Builder ──► Frontend shows dropdowns for robot/distro/middleware/engine/base preset
                           Tag derived reactively from selections (:sloretz / :osrf / :latest / :noble)
Quick Start (Local / OpenShift) ──► Two presets: Local = host-native arch; OpenShift = amd64.
                           Both set dropdowns, saveSimulationConfig, scroll to Phase 1 (no auto-build)
User clicks "Save"     ──► Frontend calls saveSimulationConfig(config)
                           ──► Backend persists to Podman Desktop configuration API

Phase 1 Build & Push   ──► buildBaseImage (same progress/cancel/push flow as base builds)
Phase 2 Build & Push   ──► buildSimulationImage (FROM local base via LOCAL_BASE_IMAGE build-arg)
----

==== Why two-phase (base + simulation)?

The build is split into a **base image** (Phase 1) and a **simulation image** (Phase 2) that layers on top via `FROM $LOCAL_BASE_IMAGE`. This is a practical optimization, not a hard technical requirement — a single Containerfile would work.

[cols="1,3"]
|===
| Benefit | Detail

| Build speed
| The base image (ROS2 core, ~1–2 GB of apt packages) rarely changes. When you modify an entrypoint, world file, or noVNC config, only the sim layer rebuilds (~5 min) instead of the full ROS2 install (~15–20 min).

| Shared foundation
| Multiple simulation images can share the same base. Today: Humble base + Humble TurtleBot3 sim, Jazzy base + Jazzy arm64 sim. Future robot types (TurtleBot4, custom URDF) layer on the same base without rebuilding ROS2 each time.

| Smaller pushes
| If `ros2-jazzy-base:noble` is already on Quay, pushing a new sim variant only transfers the diff layers (Gazebo + noVNC + packaged Nav2 deps), not the entire ROS2 stack again.

| Non-simulation use
| The base image works standalone for headless ROS2 development, CI pipelines, or robots that don't need Gazebo/noVNC.
|===

If you only ever build one sim image and never reuse the base, the split is overhead for no gain. It pays off when you have multiple images sharing a common ROS2 layer or iterate frequently on the sim layer.

== Container Architecture

=== Single Robot Container (Story 6, implemented)

Uses a single Podman container (not a pod) with all components baked in. This avoids K8s/pod overhead that caused OOM on arm64 Macs.

[source]
----
┌─── Podman Container: pai-sim-<timestamp> ──────────────────────────┐
│    Image: ros2-jazzy-sim:noble                                     │
│    Labels: io.physical-ai.role=simulation                          │
│                                                                    │
│  ┌──────────────────────────────────────────────────────────────┐  │
│  │  Ubuntu 24.04 + ROS2 Jazzy + Gazebo Harmonic + noVNC         │  │
│  │  (Nav2 packages in image; stack not launched locally)        │  │
│  │                                                              │  │
│  │  Xvfb (:99) → openbox → x11vnc → websockify (port 6080)      │  │
│  │                              ↑                               │  │
│  │  gz sim (server) ──► gz sim (GUI, renders to :99)            │  │
│  │                                                              │  │
│  │  arm64: virtio-gpu via /dev/dri (default); llvmpipe fallback │  │
│  │  in-cluster amd64: llvmpipe + headless EGL (or NVIDIA GPU)   │  │
│  │  Ogre2 Sensors plugin enabled (re-verified 2026-08)          │  │
│  └──────────────────────────────────────────────────────────────┘  │
│                                                                    │
│  Exposed ports: 6080 (noVNC), 8080 (landing page)                  │
│  Robot spawn: podman exec -d → /entrypoint-spawn-robot.sh          │
└────────────────────────────────────────────────────────────────────┘
----

==== Why a single container (not a pod)?

The original plan (Story 2/5) used a Podman pod with separate ROS2, Gazebo, and noVNC containers. On Mac Apple Silicon (arm64), the combined memory pressure of the K8s-style setup caused OOM at 4 GiB. A single container with Gazebo + noVNC baked in eliminates infra container overhead and fits within the default Podman VM (5.7 GB). Robot spawn via `podman exec` adds TurtleBot3 instances into the running container without additional containers.

=== Zenoh Middleware Foundation (done, single-container/pod — APPENG-5775)

`rmw_zenoh_cpp` is baked into the `ros2-jazzy-sim` image alongside the default DDS RMW
(`rmw_cyclonedds_cpp`/`rmw_fastrtps_cpp`) — middleware is a **runtime choice**
(`RMW_IMPLEMENTATION`), not a separate image/build. Today every ROS2 node still runs as
a process inside **one** container (Podman) or **one** pod (OpenShift) — a single
network namespace, so there is no cross-container/cross-pod DDS multicast problem to
solve yet. When `zenoh` is selected, `entrypoint-gazebo.sh` starts the Zenoh router
(`rmw_zenohd`) as a background daemon in that same container/pod before any other
ROS2/Gazebo process starts; every node (including ones launched later via `podman
exec`/`oc exec` for robot spawn and Nav2) discovers it at `rclcpp` init because those
exec'd processes inherit the container's env with zero extra code.

[source]
----
┌─────────── Container / Pod ───────────┐
│  Gazebo + TurtleBot3 + Nav2 (ROS2)     │
│  RMW_IMPLEMENTATION=rmw_zenoh_cpp      │
│           │                            │
│           ▼                            │
│      rmw_zenohd (background daemon)    │
└─────────────────────────────────────────┘
----

There is no bridge and no sidecar in this design — `rmw_zenoh_cpp` talks Zenoh
natively, and the single router in-container/pod is enough because nothing crosses a
container/pod boundary yet.

=== Multi-Robot / Multi-Pod Fleet (planned, later phase)

NOTE: Story 6 uses `podman exec` to spawn additional robots into a **single** simulation container (lightweight demo). **Story 3** targets **Podman Compose** for a real multi-container fleet (APPENG-5774), then a fleet panel (APPENG-5776) building on the Zenoh foundation above. Kind revisit still prefers one sim Deployment for packaging spikes (plan Story 5 lean Kind note, 2026-08-10); Compose/OpenShift multi-service is the fuller path. On OpenShift, the equivalent later phase is the Nav2-per-pod split with a shared `zenoh-router` pod/Service described in link:stories/story7-multipod-openshift-architecture.md[story7-multipod-openshift-architecture.md] — deliberately **not** implemented yet; this pass only lays the per-container/per-pod groundwork (image + runtime env + router daemon) that phase will build on.

== Key Technical Decisions

[cols="1,2,2"]
|===
| Decision | Choice | Rationale

| Extension template
| Full template (3-package)
| Extension has substantial UI — catalog, dashboards, panels

| Frontend framework
| Svelte 5 + TailwindCSS
| Podman Desktop standard; layout via Tailwind, theming via `.pai-*` classes in `app.css` using `--pd-*` CSS variables

| Frontend-backend communication
| MessageProxy RPC with frontend polling
| Podman Desktop webview does not deliver unsolicited backend-to-frontend messages, so frontend polls for progress (every 500ms while active)

| Routing
| tinro (hash mode)
| Required for webview context; state persisted via `PodmanDesktopApi.setState()`

| Build tooling
| Vite 8
| Fast builds, native TypeScript support, matches Podman Desktop ecosystem

| Container base (Jazzy)
| Ubuntu 24.04 (interim)
| Jazzy has no official Fedora packages (REP 2000: Ubuntu Noble Tier 1, RHEL 9 Tier 2). Official Jazzy RPMs exist for RHEL — UBI/RHEL is a nearer Red Hat path than Fedora. Migration parked; see APPENG-5809 and plan research notes.

| Container base (simulation)
| Digest-pinned presets (sloretz multi-arch, osrf amd64-only, jazzy / jazzy-noble)
| Presets ensure reproducible builds. `jazzy-noble` is the multi-arch Quick Start path. Pinned digests in `SimulationBaseImages.ts`, bumped deliberately.

| DDS is the ROS2 default. `rmw_zenoh_cpp` foundation (APPENG-5775) is implemented for the single-container/single-pod case (router runs as a background daemon); the cross-container/cross-pod fleet win still needs Story 3's Compose topology or the OpenShift multi-pod split (story7)

| Enables cancel-in-flight with double-completion guards; progress marked done immediately on cancel

| Quay catalog / registry checks

| Build/push UI

| Extracted from duplicated code; handles full build/push/cancel lifecycle with polling; used by Image Builder (SimulationSetup)

| Progress log capping
| 500-line cap via `appendProgressLog()`
| Prevents memory bloat from long builds; truncation marker shown

| SBOM format (Layers wizard `syft` tool)
| CycloneDX-JSON default (user-selectable to SPDX), `syft dir:/ -o <format> --select-catalogers -file`
| Confirmed empirically on a real 2588-package robotics image (APPENG-6226): SPDX-JSON's `externalRefs` generate many combinatorial CPE vulnerability-matching variants per package (one package alone had 49) — pushed the SBOM to 84MB. CycloneDX-JSON stores one `cpe` field per component instead, ~54% smaller for the same content. Separately, syft's file-integrity catalogers (`file-content`/`-digest`/`-executable`/`-metadata`) add one component *per file* in the image (a SHA-1/SHA-256 hash manifest) unrelated to what's installed — 115,498 of a real 118,086-component CycloneDX SBOM (97.8%) were these file-hash entries; `--select-catalogers -file` drops them with zero loss of real package data (40.5MB → 6.9MB on the same image). Both fixes are independent and compound: format choice fixes SPDX's per-package bloat, the cataloger flag fixes the per-file bloat that affects both formats (SPDX barely, CycloneDX heavily).

| Simulation container model
| Single container (not pods)
| Pod-based approach (Story 2/5) caused OOM at 4 GiB on arm64. Single container with Gazebo + noVNC baked in fits default 5.7 GB Podman VM. Nav2 packages are in the image but the navigation stack is not launched locally.

| Robot spawn mechanism
| `podman exec -d` via `process.exec()`
| Podman Desktop `containerEngine` API has no `exec` method. `process.exec('podman', ['exec', ...])` runs `/entrypoint-spawn-robot.sh` detached in the running container.

| Bash entrypoints vs Podman APIs
| Keep in-image scripts; use PD/Podman for lifecycle + exec only
| Podman/`@podman-desktop/api` manage images and containers (create/start/stop/list/build). They do not provide ROS 2/DDS, Gazebo spawn, or the Xvfb/noVNC stack. Entrypoints (`entrypoint-gazebo.sh`, `entrypoint-spawn-robot.sh`, …) orchestrate that stack inside the image; Topic Monitor / Peek / nav use `podman exec` + ROS CLI (`#execRosBash`). A native ROS client or in-container bridge would reduce CLI execs but is a separate architecture bet — not “replace scripts with Podman.” Internal detail: `.internal/tech-reference.md` (Bash scripts vs Podman).

| Ogre2 Sensors on arm64
| Re-enabled in world SDF (2026-08)
| 2026-07 segfault not reproduced on current Gazebo Harmonic + Mesa (llvmpipe or virtio-gpu), verified with `scripts/test-sensors-gpu.sh`. **Caveat:** this covers only the arm64/virtio-gpu render path — see the in-cluster row below for amd64/llvmpipe.

| In-cluster sensor rendering (amd64, no GPU)
| Off-screen EGL for the Gazebo server
| On OpenShift (amd64, pure **llvmpipe**, no GPU) the sensors plugin's Ogre2/GL3Plus tries to create an on-screen **GLX** window and **SIGSEGVs (exit 139)** the moment a sensor-bearing robot spawns (`SensorsPrivate::RenderThread → Ogre2RenderEngine::CreateRenderWindow → GL3PlusRenderSystem::_createRenderWindow`); with no liveness probe the pod restarts and every spawned robot is wiped ("robots vanished + noVNC won't reconnect"). The arm64/virtio-gpu "no segfault" check did **not** cover this — different render path. **Fix:** render the server off-screen via **EGL** — `entrypoint-gazebo.sh` software path exports `EGL_PLATFORM=surfaceless` + `gz sim -s --headless-rendering`; `Containerfile` adds `libgl1-mesa-dri libegl-mesa0 libgbm1`. Keeps `/scan` for Nav2. Full detail: `.internal/tech-reference.md` (in-cluster rendering) and Story 4/6.

| In-cluster GPU rendering (deploy-time toggle)
| "Cluster has a GPU" checkbox on Deploy to OpenShift
| One amd64 image serves both cluster types without a rebuild. **Off (default):** software env forces llvmpipe + headless EGL (row above). **On:** Deployment requests `nvidia.com/gpu: 1` and sets `PHYSICAL_AI_USE_GPU=1`; the entrypoint sees a GPU request without `/dev/dri` (the NVIDIA GPU operator exposes `/dev/nvidia*`, not DRI) and renders off-screen via **hardware EGL** (`--headless-rendering`, no surfaceless override). GPU-on path is **implemented but unverified** (no GPU cluster available).

| In-cluster CPU sizing (no GPU)
| Configurable, default 8 guaranteed CPUs for the software-rendering pod (validated from 6)
| With software rendering the Gazebo GUI client (`gz sim -g`, rendering the scene for noVNC) alone needs **~2.3 cores**, and during *active* navigation Nav2's planner/controller/costmaps add **~1 more**. Sweep verified live on `sgahlot-pd-extn` (2026-08-14): **2 cores → RTF ~0.01–0.14 → `navigate_to_pose` never finishes (UI hangs on "Navigating…"); 4 cores → goals complete but active-nav utilization hits ~90%, so RTF sags to ~0.3–0.6 → slow, jerky motion; 6 cores → ~60% utilization with headroom → RTF ~1.0, smooth (a warm ~2 m trip in ~33 s)**. The Deployment default is now **8 CPUs (requests == limits, guaranteed)** — configurable 1–64 via the **Software-render CPUs** field, raised from the validated 6 for active-nav headroom and multi-robot. The bottleneck is the GUI, **not** the depth camera (server-side sensors ~0.4 core), so dropping sensors would not lower the floor — a GPU would. The residual micro-stutter from CFS throttling (the container sees 16 host CPUs but is capped at the pod quota, so Gazebo/Ogre thread bursts get throttled) is removed by the **Story 5 thread caps** (GUI llvmpipe pool clamped to 2). The GPU pod is a fixed **7 CPUs** (`GPU_POD_CPU`); on the no-`/dev/dri` cluster the GUI stays software-rendered, so it still needs the cores. Detail: `.internal/tech-reference.md` (in-cluster rendering).

== Resolved Questions

* **noVNC vs alternatives:** noVNC chosen and implemented. Xvfb + x11vnc + websockify stack baked into the simulation image, served on port 6080. Lightweight and works without GPU.
* **Mac GPU and rendering:** On arm64 Mac, simulation launch passes `/dev/dri` and sets `PHYSICAL_AI_USE_GPU=1` (preference **Simulation GPU passthrough**, default on). The entrypoint uses virtio-gpu when `/dev/dri` is present; otherwise falls back to `llvmpipe`. amd64 always uses software rendering. Xvfb + noVNC stack is unchanged.
* **Ogre2 Sensors plugin:** Re-enabled in world SDF (2026-08). A 2026-07 segfault under llvmpipe is **not reproduced** on current Gazebo Harmonic + Mesa (`scripts/test-sensors-gpu.sh`) — **on arm64/virtio-gpu**. Lidar (`/scan`) and IMU publish after spawn; on Jazzy, Nav2 is launched locally for the **Navigate** button (`navigate_to_pose`, APPENG-5981) — see Nav2 row in Key Technical Decisions.
* **In-cluster sensor rendering (amd64/llvmpipe):** The arm64 "no segfault" result does **not** carry over to OpenShift. On amd64 with pure llvmpipe (no GPU) the sensors plugin still **SIGSEGVs** on spawn (on-screen GLX under software GL). Fixed by rendering the Gazebo server off-screen via **EGL** (`--headless-rendering` + `EGL_PLATFORM=surfaceless` + mesa-EGL packages). A deploy-time **"Cluster has a GPU"** toggle switches to hardware EGL (`nvidia.com/gpu`) for GPU clusters (unverified). See the two in-cluster rows in Key Technical Decisions and `.internal/tech-reference.md`.
* **In-cluster Navigate hang (no GPU):** After the EGL fix, Navigate initially hung on "Navigating…" in-cluster. Root cause was **two independent bugs**, neither in the Nav2/TF/bridge logic (that stack was healthy). (1) The extension's `oc exec` ROS calls ran with `HOME=/` (not writable), so every rclcpp command aborted (`Failed to create log directory`) and the goal never reached Nav2 — fixed by exporting `HOME`/`ROS_HOME`/`ROS_LOG_DIR` on the `oc` path. (2) **CPU sizing**: once goals flowed, 2 cores pinned RTF at ~0.1 (never finishes) and 4 cores sagged to ~0.3–0.6 during active nav (slow/jerky); raising the software-rendering pod to **6 guaranteed CPUs** gives RTF ~1.0 and smooth navigation (warm ~2 m trip ~33 s); the default was later raised to a configurable **8 CPUs** (GPU pod fixed at **7**). See the "In-cluster CPU sizing" row in Key Technical Decisions and `docs/stories/story4-followups.md`.
